# ТЗ: Modbus-карты слейвов для совместимости с greenhouse-hub

## Цель

Документ задает правила, по которым Modbus RTU слейвы должны строить свои
карты регистров, чтобы `greenhouse-hub` мог обнаруживать устройства, опрашивать
телеметрию, публиковать состояние в HTTP API и записывать уставки по ключам.

ТЗ относится ко всем контроллерам-слейвам на RS485-шине, где единственным
Modbus-мастером является `greenhouse-hub`.

## Термины

- `slave` - полевой контроллер на Modbus RTU.
- `hub` - сервис `greenhouse-hub` на Ubuntu Server.
- `slave map` - JSON-описание карты, которое hub загружает из
  `greenhouse-hub/slave_maps` или `/etc/greenhouse/slave_maps`.
- `register address` - zero-based адрес holding register, который используется
  в запросах hub.
- `key` - стабильное логическое имя регистра в JSON-карте.

## Обязательный транспортный контракт

1. Слейв должен поддерживать Modbus RTU holding registers.
2. Hub использует function code `3` для чтения, `6` для записи одного регистра
   и `16` для записи блока регистров.
3. Адресация регистров - zero-based. В JSON-карте обязательно:

```json
"addressing": "zero_based_holding_register"
```

4. Один регистр - 16-битное слово. Многословные значения должны быть явно
   описаны в карте через диапазон `from`/`to`.
5. Слейв должен корректно отвечать на чтение до 125 регистров и запись до 123
   регистров, либо возвращать стандартное Modbus-исключение для неподдерживаемых
   диапазонов.
6. `slave_id` задается топологией. Прошивка не должна считать, что тип
   устройства всегда имеет фиксированный адрес на шине.

## Обязательный identity-блок

Hub определяет тип и совместимость слейва чтением holding-регистров `0..15`.
Эти регистры обязательны для каждого совместимого слейва.

| Регистр | Key | Тип | Доступ | Требование |
| --- | --- | --- | --- | --- |
| 0 | `device_type` | `u16` | `r` | Тип устройства. Должен совпадать с JSON-картой в каталоге hub. |
| 1 | `firmware_version` | `u16` | `r` | Версия прошивки, рекомендуемый формат `major << 8 | minor`. |
| 2 | `modbus_map_version` | `u16` | `r` | Версия карты. Должна совпадать с JSON-картой в каталоге hub. |
| 3 | `zone_id` | `u16` | `r` | Номер зоны или `65535` для общего устройства, например метеостанции. |
| 4 | `capability_low` | `u16` | `r` | Биты возможностей `0..15`. |
| 5 | `capability_high` | `u16` | `r` | Биты возможностей `16..31`. |
| 6 | `status_bits` | `u16` | `r` | Общий битовый статус. |
| 7 | `fault_code` | `u16` | `r` | Основная активная ошибка, `0` - ошибок нет. |
| 8 | `uptime_hi` | `u16` | `r` | Старшее слово счетчика uptime. |
| 9 | `uptime_lo` | `u16` | `r` | Младшее слово счетчика uptime. |
| 10 | `last_master_age_s` | `u16` | `r` | Возраст последнего валидного запроса мастера в секундах. |
| 11 | `restart_counter` | `u16` | `r` | Счетчик стартов прошивки. |
| 12 | `config_version` | `u16` | `r` | Версия конфигурации слейва. |
| 13 | `serial_hi` | `u16` | `r` | Старшее слово серийного номера. |
| 14 | `serial_lo` | `u16` | `r` | Младшее слово серийного номера. |
| 15 | `identity_crc` | `u16` | `r` | CRC/check word identity/config-блока или `0`, если не используется. |

Hub сопоставляет слейв с картой по паре:

```text
device_type + modbus_map_version
```

Если такой пары нет среди загруженных JSON-карт, слейв считается
неподдерживаемым.

Текущие назначенные типы устройств:

| Device type | Назначение | Текущая карта |
| --- | --- | --- |
| 1 | Zone slave | `greenhouse-hub/slave_maps/zone_v1.json` |
| 2 | Weather station | `greenhouse-hub/slave_maps/weather_v1.json` |

Новые `device_type` нужно резервировать до выпуска прошивки.

## Общий план регистров

Все совместимые карты должны придерживаться общего плана адресов, если для
нового `device_type` явно не описан другой план и не добавлена поддержка в hub.

| Диапазон | Назначение | Типовой доступ |
| --- | --- | --- |
| `0..99` | Identity, статус, диагностика | Read-only |
| `100..399` | Резерв/common service | Reserved |
| `400..699` | Телеметрия и runtime-статус по типу устройства | Read-only |
| `700..999` | Статус применения данных от hub/service status | Read-only |
| `1000..1299` | Уставки и команды от hub | Read/write где объявлено |
| `1300..1599` | Расписания и профили | Read/write где объявлено |
| `1600..1799` | Общие внешние данные | Read/write где объявлено |
| `1800..1999` | Расширенная диагностика/debug | Смешанный, ограниченный |

Зарезервированные регистры должны читаться и возвращать `0`, если для
конкретного типа устройства не описано иное поведение.

## Требования к JSON-карте

Для каждой производственной версии прошивки должна существовать соответствующая
JSON-карта в каталоге hub. Имя файла не является частью протокола, но
рекомендуется формат:

```text
<device_family>_v<modbus_map_version>.json
```

Обязательные верхнеуровневые поля:

```json
{
  "schema": "greenhouse_slave_map_v1",
  "name": "Zone Slave Map v1",
  "device_type": 1,
  "device_type_name": "Zone Slave",
  "modbus_map_version": 1,
  "addressing": "zero_based_holding_register",
  "deprecated_aliases_supported": false,
  "ranges": [],
  "common": [],
  "capabilities": [],
  "telemetry": [],
  "setpoints_commands": [],
  "schedules_profiles": [],
  "shared_external_data": [],
  "advanced_diagnostics": [],
  "write_policy": {
    "writable_ranges": [],
    "read_only_ranges": []
  }
}
```

Регистр описывается либо одиночным адресом:

```json
{"reg": 400, "key": "air_temp", "type": "s16", "scale": 0.1, "unit": "degC", "access": "r"}
```

либо непрерывным блоком:

```json
{"from": 430, "to": 443, "key": "windows_runtime_status", "type": "u16", "access": "r"}
```

Поля элемента регистра:

| Поле | Обязательность | Смысл |
| --- | --- | --- |
| `reg` | Для одиночного регистра | Zero-based адрес. |
| `from`, `to` | Для блока | Включительный диапазон zero-based адресов. |
| `key` | Да | Стабильное API-имя. Должно быть уникальным в карте. |
| `type` | Рекомендуется | Сейчас hub декодирует `u16` и `s16`. |
| `access` | Да | `r`, `rw` или `w`. |
| `scale` | Опционально | Множитель физической величины: raw `235`, scale `0.1` = `23.5`. |
| `unit` | Опционально | Единица отображения/диагностики. |
| `capability_bit` | Опционально | Регистр имеет смысл только при наличии этого capability. |
| `note` | Опционально | Короткое примечание или описание enum. |
| `format` | Опционально | Описание packed-формата. |
| `default` | Опционально | Заводское raw-значение. |
| `examples` | Опционально | Примеры допустимых raw-значений. |

## Правила для key

1. `key` - публичное стабильное имя. Нельзя переименовывать key внутри той же
   пары `device_type + modbus_map_version`.
2. Нельзя использовать существующий key для другого смысла.
3. Нельзя переносить существующий key на другой регистр без увеличения
   `modbus_map_version`.
4. Рекомендуемый стиль - lower snake_case.
5. Для уставок нужно использовать существующие префиксы, чтобы hub правильно
   группировал элементы для API клиента:

| Префикс | Группа hub |
| --- | --- |
| `water_` | Water |
| `windows_`, `window_`, `rll400_`, `actuator_` | Windows |
| `heating_` | Heating |
| `curtain_` | Curtain |
| `co2_` | CO2 |
| `side_curtain_` | Side curtain |
| `circ_` | Circulation |
| `light_` | Light |
| `weather_` | Weather |

## Capabilities

Capabilities - 32-битная маска:

```text
capability_mask = capability_low | (capability_high << 16)
```

JSON-карта должна перечислять все назначенные биты:

```json
{"bit": 7, "key": "windows_group_a"}
```

Прошивка должна устанавливать бит только если соответствующая функция или
аппаратная часть реально есть и ее регистры имеют смысл. Hub использует маску,
чтобы помечать группы уставок как supported/unsupported.

Назначенные биты Zone slave v1:

| Bit | Key |
| --- | --- |
| 0 | `air_temperature` |
| 1 | `air_humidity` |
| 2 | `co2` |
| 3 | `water_rail_temperature` |
| 4 | `water_grow_temperature` |
| 5 | `water_undertray_temperature` |
| 6 | `water_upper_heat_temperature` |
| 7 | `windows_group_a` |
| 8 | `windows_group_b` |
| 9 | `curtain` |
| 10 | `heating_output` |
| 11 | `lighting_output` |
| 12 | `weather_sync_input` |
| 13 | `autonomous_mode` |
| 14 | `manual_mode` |

## Требования к телеметрии

1. Телеметрические регистры должны быть перечислены в секции `telemetry`.
2. Hub читает регистры из `telemetry`, объединяет соседние адреса в
   непрерывные read spans и выполняет Modbus-чтение по этим span.
3. Одиночная телеметрия публикуется в состоянии hub как
   `slave_<slave_id>.<key>`.
4. Блоки `from`/`to` hub читает, но текущая реализация не публикует каждое
   слово блока отдельной точкой, если оно не объявлено отдельным single-регистром.
5. Знаковые значения должны иметь `type: "s16"` и храниться в two's complement.
6. Масштабирование задается через `scale`:

```text
decoded_value = raw_value * scale
```

Для `s16` raw сначала интерпретируется как signed 16-bit.

## Требования к уставкам и командам

1. Записываемые оператором регистры должны быть описаны в одной из секций:
   `setpoints_commands`, `schedules_profiles`, `shared_external_data`.
2. Записываемый key должен иметь `access: "rw"` или `access: "w"`.
3. Этот же диапазон должен быть разрешен в `write_policy.writable_ranges`.
4. Этот же диапазон не должен пересекаться с `write_policy.read_only_ranges`.
5. Hub пишет по key: находит стартовый регистр в JSON-карте и использует
   function `6` для одного значения или function `16` для нескольких значений.
6. Для одиночных UI/SCADA-контролов каждый control нужно объявлять отдельным
   `reg`. Не нужно прятать независимые controls внутри общего блока.
7. Для много-регистровых блоков используется `from`/`to`; hub разрешит payload
   от `1` слова до ширины блока и начнет запись с адреса `from`.
8. Прошивка должна сама валидировать диапазоны значений и безопасно отвергать
   семантически неверные команды.
9. Карты должны задавать `deprecated_aliases_supported: false`, если специально
   не реализована обратная совместимость.

Пример одиночной уставки:

```json
{"reg": 1030, "key": "windows_ctrl_mode", "type": "u16", "access": "rw", "note": "0=AUTO, 1=MANUAL"}
```

Пример соответствующей write policy:

```json
"write_policy": {
  "writable_ranges": [
    {"from": 1030, "to": 1030}
  ],
  "read_only_ranges": [
    {"from": 0, "to": 99},
    {"from": 400, "to": 999}
  ]
}
```

## Версионирование

`modbus_map_version` нужно увеличивать, если:

- существующий key переносится на другой регистр;
- у существующего key меняется тип, scale, unit, access, enum или смысл;
- существующий регистр получает другой смысл;
- меняется write policy так, что это влияет на hub или клиент;
- меняется семантика identity-блока или capability bits.

Версию можно не менять только при добавлении новых регистров в ранее
зарезервированное место, если все существующие key, адреса, scale и поведение
остались прежними. Для production-релизов при сомнениях версию лучше увеличить.

Старая JSON-карта должна оставаться в каталоге hub, пока на объекте есть хотя
бы один слейв со старым `modbus_map_version`.

## Требования к поведению прошивки

1. Регистры `0..15` должны быть доступны сразу после старта.
2. Пока устройство инициализируется, телеметрия может возвращать безопасные
   значения по умолчанию, но `status_bits`/`fault_code` должны показывать, что
   данные еще не готовы.
3. Read-only регистры должны игнорировать запись или возвращать Modbus-исключение.
4. Для command-token регистров должны быть описаны регистры подтверждения и
   результата, если клиенту нужно понимать итог применения команды.
5. Запись одного Modbus-запроса должна применяться атомарно там, где это важно
   для безопасности.
6. Небезопасные команды должны завершаться fail-safe. Например, контроллер
   форточек при устаревших weather-данных должен применять свою safe policy.
7. Автономная логика управления остается внутри слейва. Hub только передает
   уставки, общие данные и телеметрию.

## Процесс выпуска новой карты

Для каждой новой или измененной карты прошивки:

1. Добавить JSON-карту в `greenhouse-hub/slave_maps/`.
2. Проверить уникальность пары `device_type + modbus_map_version`.
3. Проверить, что прошивка возвращает те же `device_type` и
   `modbus_map_version` в регистрах `0` и `2`.
4. Добавить/обновить топологию с нужным `slave_id` и типом модуля.
5. Запустить тесты hub:

```text
cd greenhouse-hub
go test ./...
```

6. В mock-режиме или на железе проверить:
   - `GET /api/slaves` показывает слейв как `supported: true`;
   - `GET /api/slaves/{slave_id}/setpoints` возвращает ожидаемые группы;
   - `POST /api/setpoints` пишет именно ожидаемый регистр;
   - read-only ключи отвергаются write policy hub.

## Критерии приемки

Карта и прошивка считаются совместимыми с `greenhouse-hub`, если:

1. Hub читает регистры `0..15` без таймаута.
2. Пара `device_type + modbus_map_version` совпадает с загруженной JSON-картой.
3. Hub показывает слейв online и supported.
4. Все регистры из `telemetry` читаются function code `3`.
5. Телеметрия декодируется с правильным знаком, scale и unit.
6. Каждый writable key из `GET /api/slaves/{slave_id}/setpoints` пишет только
   свой документированный регистр или блок.
7. Все read-only диапазоны заблокированы через `write_policy`.
8. Capability bits соответствуют установленному оборудованию и правильно
   включают/выключают группы уставок.
9. Обновление прошивки без изменения `modbus_map_version` не ломает ни один
   существующий key, адрес, scale или write behavior.

## Частые ошибки

- Использовать one-based номера регистров в JSON-карте.
- Возвращать в регистре `2` версию, которая не совпадает с JSON-картой.
- Переносить регистр, но оставлять прежние key и `modbus_map_version`.
- Указывать `access: "rw"` без добавления диапазона в
  `write_policy.writable_ranges`.
- Разрешать запись в identity или telemetry ranges.
- Делать один большой block key для параметров, которые оператор должен менять
  независимо.
- Устанавливать capability bit для отсутствующего оборудования.
- Описывать телеметрию только блоком `from`/`to` и ожидать, что текущий hub
  опубликует каждое слово отдельной именованной точкой.
